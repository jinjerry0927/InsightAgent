## 2026-10-23 — Phase 0 설계 승인

| 개념 | 쉬운 설명 | 프로젝트에서 확인할 점 |
| --- | --- | --- |
| SQL | 어떤 데이터를 어떤 기준으로 계산할지 적는 명령 | 질문과 기간·조건·집계 단위가 같은가 |
| DuckDB | 로컬 데이터 분석용 계산 창구 | 원본에서 재현 가능하게 적재되고 실제 결과가 조회되는가 |
| KPI 정의 | 같은 "매출"을 모두 같은 방식으로 계산하기 위한 약속 | 금액 종류·배송비·주문 상태·날짜 기준을 승인했는가 |
| 연결 중복 | 여러 상품과 여러 결제를 바로 연결하면 행이 늘어나는 현상 | 연결 전후 행 수와 주문별 집계 기준이 맞는가 |
| 모의 객체 | 실 API 대신 준비된 응답을 돌려주는 테스트 대역 | 성공·실패·한도를 비용 없이 반복 검증할 수 있는가 |

설명용 예시: 주문 1건에 상품 2행·결제 3행이 있을 때 바로 연결하면 6행이 될 수 있다. 실제 Olist 통계가 아니며, 중복 집계 위험을 설명하기 위한 예다.

Phase 0 확인 질문:

1. SQL이 오류 없이 실행되어도 분석 결과가 정확하다고 바로 판단할 수 없는 이유는 무엇인가?
2. 여러 상품·결제 행을 연결한 뒤 매출 합계를 다시 확인해야 하는 이유는 무엇인가?

사용자의 이해 답변은 아직 기록되지 않았다. 설계 승인을 이해 확인 답변으로 간주하지 않는다.

## 2026-10-23 — Phase 1 역분석

| 개념 | 쉬운 설명 | 이번 조사에서 얻은 점 |
| --- | --- | --- |
| 도구 호출 | 모델이 직접 DB를 조작하는 대신 프로그램에 SQL 실행을 요청하는 것 | 모델의 요청과 프로그램의 실행 책임을 분리할 수 있다 |

| 실행 권한과 SQL 안전성 | 창구 이용 자격과 요청 내용의 안전성은 별도 검사다 | 그룹 권한 통과만으로 변경·외부 접근·과도한 계산을 막지는 못한다 |
| 제한된 작업 루프 | 정해진 횟수 안에서 생성·검사·조회하고 종료하는 절차 | 도구 라운드, 모델 호출, SQL 실행 횟수를 혼동하지 않아야 한다 |
| 소스 근거 | 특정 버전의 특정 코드 위치로 설명을 확인하는 것 | README와 실제 메서드가 다를 수 있어 커밋·라인을 함께 기록한다 |

| 개념 | 쉬운 설명 | 이번 프로젝트에서 확인할 점 |

| 직접·하위 의존성 | 직접 쓰는 패키지와 그 패키지가 필요로 하는 다른 패키지 | 직접 3개를 선택해도 설치는 총 12개가 될 수 있다 |

환경 설정 검토 질문:

2. 환경 확인 스크립트가 통과해도 Olist 매출 계산이 정확하다고 말할 수 없는 이유는 무엇인가?

Phase 2 전체 완료는 실제 데이터 조사·적재와 KPI 검토 후 판단한다.

## 2026-10-24 — Phase 2 실제 데이터·GitHub

- CSV 9개를 그대로 보존해 적재했다. 타입 변환과 품질 조사는 비즈니스 KPI 계산 전의 준비 작업이다.
- 실제 주문은 99,441행이지만 상품·결제·리뷰를 한꺼번에 LEFT JOIN하면 119,143행이다. JOIN의 실행 성공이 집계 정확성을 뜻하지 않는다.
- customer_id는 주문 연결용이고 customer_unique_id는 여러 주문의 같은 고객을 연결한다. 후기 분석은 주문별 다중 리뷰 대표 선택이 필요하다.
- 구매일 범위와 배송·리뷰·발송기한 범위는 다르다. 구매 행이 없는 월도 있어 전체 최솟값·최댓값만으로 데이터 존재를 보장할 수 없다.
- Commit은 변경 기록, Branch는 독립 작업 공간, PR은 변경 검토 요청, Issue는 작업·오류 기록, Actions는 코드 변경 시 자동 검증이다.
- GitHub 자동 검증은 원본 데이터 없이 합성 입력으로 코드 동작을 검사한다. 실제 데이터의 행 수·기간·품질은 별도 로컬 보고서로 증명한다.

Phase 2 검토 질문:

1. 주문 99,441행이 JOIN 후 119,143행이 되었다면 상품금액 합계와 주문수를 어떤 단위에서 먼저 계산해야 할까?
2. 배송 지연율을 구할 때 delivered지만 배송일이 NULL인 주문을 자동으로 정상 배송으로 처리하면 어떤 문제가 생길까?

## 2026-10-24 — Phase 3 기준 SQL과 독립 검증

- 기준 SQL은 AI가 만든 SQL의 정확도를 비교할 기준점이다. 먼저 KPI 정의를 승인하고 AI 없이 계산을 재현한다.
- 상품을 주문 단위로 먼저 합산해 리뷰·결제의 다중 행이 상품금액에 영향을 주지 않도록 했다.
- 합성 예제에서 상품금액은 1월 41.00, 2월 18.00이다. 큰 결제·배송비·취소 주문을 넣어도 이 합계가 바뀌지 않아야 한다.
- 관측된 0원 주문, 조회 조건의 데이터 부재, 상품·가격 결측은 서로 다르다. 자동으로 모두 0으로 바꾸지 않는다.
- 원본 CSV의 Decimal 독립 계산으로 SQL 결과를 대조했다. 1센트 차이와 부동소수 금액으로의 변환도 검증 실패로 탐지한다.
- 월별 비율 평균 대신 월별 지연 건수·비교 가능 주문수를 합쳐 전체 비율을 계산한다.
- 최신 리뷰는 전체 스냅샷 기준이다. 구매 기간 뒤에 작성된 리뷰도 포함될 수 있어 과거 시점 당시 의견과 구분해야 한다.
- 현재 설치·데이터 이동·Git 명령·테스트 실행은 Codex가 수행한다. 사용자는 결과와 중요한 설계 결정을 검토하며, API 키 설정은 필요한 Phase에서 별도 안내한다.

Phase 3 확인 질문:

2. 2017년 구매 주문의 대표 리뷰가 2018년에 작성되었다면 이 분석은 어떤 시점의 의견을 보여주는가?

학습 질문 답변은 개발 진행 조건으로 요구하지 않는다. Phase 4 착수는 별도 사용자 검토·승인 대상이다.
