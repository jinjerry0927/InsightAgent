## 2026-10-24 — Phase 2 실제 데이터·GitHub

- CSV 9개를 그대로 보존해 적재했다. 타입 변환과 품질 조사는 비즈니스 KPI 계산 전의 준비 작업이다.
- 실제 주문은 99,441행이지만 상품·결제·리뷰를 한꺼번에 LEFT JOIN하면 119,143행이다. JOIN의 실행 성공이 집계 정확성을 뜻하지 않는다.
- customer_id는 주문 연결용이고 customer_unique_id는 여러 주문의 같은 고객을 연결한다. 후기 분석은 주문별 다중 리뷰 대표 선택이 필요하다.
- 구매일 범위와 배송·리뷰·발송기한 범위는 다르다. 구매 행이 없는 월도 있어 전체 최솟값·최댓값만으로 데이터 존재를 보장할 수 없다.
- Commit은 변경 기록, Branch는 독립 작업 공간, PR은 변경 검토 요청, Issue는 작업·오류 기록, Actions는 코드 변경 시 자동 검증이다.
- GitHub 자동 검증은 원본 데이터 없이 합성 입력으로 코드 동작을 검사한다. 실제 데이터의 행 수·기간·품질은 별도 로컬 보고서로 증명한다.

## 2026-10-24 — Phase 3 기준 SQL과 독립 검증

- 기준 SQL은 AI가 만든 SQL의 정확도를 비교할 기준점이다. 먼저 KPI 정의를 승인하고 AI 없이 계산을 재현한다.
- 상품을 주문 단위로 먼저 합산해 리뷰·결제의 다중 행이 상품금액에 영향을 주지 않도록 했다.
- 합성 예제에서 상품금액은 1월 41.00, 2월 18.00이다. 큰 결제·배송비·취소 주문을 넣어도 이 합계가 바뀌지 않아야 한다.
- 관측된 0원 주문, 조회 조건의 데이터 부재, 상품·가격 결측은 서로 다르다. 자동으로 모두 0으로 바꾸지 않는다.
- 원본 CSV의 Decimal 독립 계산으로 SQL 결과를 대조했다. 1센트 차이와 부동소수 금액으로의 변환도 검증 실패로 탐지한다.
- 월별 비율 평균 대신 월별 지연 건수·비교 가능 주문수를 합쳐 전체 비율을 계산한다.
- 최신 리뷰는 전체 스냅샷 기준이다. 구매 기간 뒤에 작성된 리뷰도 포함될 수 있어 과거 시점 당시 의견과 구분해야 한다.
- 현재 설치·데이터 이동·Git 명령·테스트 실행은 Codex가 수행한다. 사용자는 결과와 중요한 설계 결정을 검토하며, API 키 설정은 필요한 Phase에서 별도 안내한다.

## 2026-10-24 — Phase 4 API 어댑터와 모의 전송

- API 어댑터는 모델 호출 방식·오류·사용량을 한곳에서 다룬다. 모델이나 주소를 바꾸어도 이후 분석 로직이 SDK 세부 사항에 직접 의존하지 않게 한다.
- API 키는 서비스 이용 권한이다. 로컬 `.env`에서만 읽고 Git·채팅·오류 본문에 남기지 않는다. 예제 파일은 변수 이름과 비밀값 없는 기본 설정만 제공한다.
- SDK의 기본 재시도는 애플리케이션이 센 호출 수와 실제 요청 수를 다르게 만들 수 있다. 이번 어댑터는 재시도를 0으로 설정하고 429·401·시간 초과 등에서 실제 전송 1회로 끝나는지 검사한다.
- HTTP 모의 전송은 설치된 SDK의 직렬화·오류 동작을 실제 인터넷 없이 검증한다. 계정 키의 유효성이나 호스팅 모델의 실제 응답까지 증명하지 않는다.
- 출력 토큰 제한에 도달한 텍스트는 SQL이 중간에 끊겼을 수 있다. 내용이 있어도 성공으로 넘기지 않는다. 사용량이 제공되지 않으면 0이 아니라 미확인이다.
- 최소 연결 문장은 영어다. 연결 성공은 한국어 질문 처리·SQL 정확도·계정 잔여 한도 검증과 구분한다.

## 2026-10-30 — Phase 5 제한된 분석 에이전트

- AST는 SQL의 구조다. SELECT로 시작해도 파일 읽기·동적 쿼리·시스템 조회가 가능하므로 문장을 파싱하고 허용한 기능만 통과시킨다.
- 안전한 SQL과 올바른 KPI는 다른 검사다. 취소 주문 매출이나 다중 JOIN으로 부풀린 매출도 읽기 전용 SQL일 수 있다. 초기에는 네이티브 정규화 결과가 승인 기준 SQL과 일치해야 실행한다.
- 질문·기간, 생성, 검사, 실행, 수정, 종료를 명시적인 상태로 기록한다. 위험 SQL·API 인증/한도·자원 오류는 즉시 종료하며 안전한 수정은 최대 1회다.
- 모델 호출·실제 API 시도·SQL 수정·후보 DB 조회를 따로 센다. 고정 SQL 모의 객체는 모델 인터페이스를 호출해도 실제 API 시도는 0회다. 횟수 한도는 소진 목표가 아니다.
- 원본 DB는 읽기 전용으로 열고 후보 SQL에는 필요한 컬럼만 보인다. API 키·원시 오류·결과 행을 모델에 보내지 않는다. 키는 부모 API 클라이언트의 인증 헤더에만 사용한다.
- 행 LIMIT만으로는 큰 집계의 시간·메모리를 막을 수 없다. 프로세스 종료 시간과 DB 메모리 제한을 결합하되 전체 RSS·OS 권한 격리와 차이를 이해해야 한다.
- 실제 한국어 질문은 1개 검증했다. 매출 111,798.36·주문 750건은 LLM이 계산한 수가 아니라 검사를 통과한 SQL로 로컬 DB에서 얻고 기준값과 대조한 결과다.

2. 안전성 검사를 통과한 SQL을 승인된 KPI 구조와 다시 대조하는 이유는 무엇일까?
